# 平台分析模块索引

> 本目录是 `wanfeng-hit-ops` 的**分析层按平台扩展点**。
> 一个平台一个文件，互不混算；后续新增平台只加文件，不改通用方法论。

---

## 一、四层规则（冲突时按此优先级）

| 层 | 文件 | 管什么 | 能否被覆盖 |
|---|---|---|---|
| **L0 能力边界** | `../../SKILL.md` 开头「⛔ 能力边界」 | **只做数据分析与归因评估，不创作任何内容** | ❌ 最高优先级，先于以下所有规则 |
| **L1 通用纪律** | `../../SKILL.md` 开头「三个不可让步的纪律」 | 不跨平台相加、口径必须显式、算出来的与人写的分开 | ❌ 任何平台模块不得违背 |
| **L2 通用方法** | `../hit-methodology.md` | 效率指标、四象限、反例、置信度、实验设计、**§八 已发布内容评估编码** | ❌ 平台模块只做**具体化**，不改判定原则 |
| **L3 平台模块** | `references/platforms/<platform>.md` | 该平台专属口径、字段字典、涨粉漏斗、采集时机、专属分析动作 | ✅ 只在本平台内生效 |

**平台层不能新造「跨平台可比」的指标**，也不能把本平台的播放 / 观看 / 阅读拿去和其他平台做数值排名。

---

## 二、路由规则（每次分析前必做）

1. 判断本次分析涉及哪个平台（从 `账号数据/<平台>/` 路径或用户提问里读）
2. 加载 `references/platforms/<platform>.md`
3. **未实现的平台**：只按 L1 + L2 出结论，并在报告「数据缺口」里写明「该平台尚无专属模块，本次仅用通用口径」，**不要临时现编一套平台规则**
4. 多平台一起分析：每个平台分别加载自己的模块，**分节写**；第五章跨平台综合只做定性分工，不做数值排名

## 四、扩展契约：新增一个平台模块

完整骨架在 [`_template.md`](_template.md)，**必须写满 8 节**：

1. 适用范围与边界
2. 口径字典（字段名 / 含义 / 公式 / 去重维度 / 时间窗 / 来源 / 更新频率 / 变更记录）
3. 该平台的**涨粉漏斗**（每一跳怎么算、卡点怎么诊断）
4. 通用效率指标在本平台的**翻译**（分母是什么）
5. 单篇级归因（能否进四象限、缺什么数据、怎么补）
6. 专属分析动作（该平台独有的分层 / 拆分 / 对照逻辑）
7. 样本量、置信度、实验设计的平台特例
8. 报告落点 + 数据缺口必写项 + 交付清单增补

### 硬性要求

- 必须显式声明「本平台的**被看到**口径是什么」，以及**不能和哪个平台相加 / 排名**
- 必须写**采集时机**（很多平台数据有保存期限，过期永久缺失）
- 必须写**至少一条反例对照逻辑**
- **不得引入新的硬依赖**（联网 / API Key / 第三方榜单）。外部数据只能作为「可选外部输入」单开一节登记，且不得与第一方后台数据混算

## 五、与代码层的分工

`../data-pipeline.md` §五 讲的是**怎么加解析与填数代码**；本目录讲的是**怎么分析**。
两者用同一个平台名，但互不替代：

| 层 | 新增平台时要动的地方 |
|---|---|
| 代码层 | `scripts/parse_data.py`、`scripts/monthly_report.py`、`scripts/classify.py`、`templates/月度报告模板.md` |
| 分析层 | 本目录新增 `<platform>.md` + 更新本表 + 更新 `../../SKILL.md` 目录树 + 更新 `../../README.md` 版本表 |

**只加分析模块、不加解析代码是允许的**：此时模块里的「单篇级归因」必须写明数据缺口与补齐方式，不能假装能算。

---

## 六、边界

- 平台模块**只处理第一方后台导出文件**，不联网、不依赖任何 API Key
- 若后续要接入第三方榜单 / 对标账号数据，走「可选外部输入」：单开一节写明来源、口径、可信度降级规则，**不得与后台数据混算**
- **只做数据分析，不创作内容**：不产出标题 / 备选标题 / 脚本 / 正文 / 封面文案 / 选题清单 / 排期 / 变现方案。借来的评估编码（§八 `T*` / `V*`）只用于给**已发布内容**打标与分组统计
- 平台模块不预测爆款；它只回答「这个平台的数据说明了什么，以及下期该验证哪个结构」

## 七、待验证假设清单（写各平台模块时的起点）

> 以下是从外部内容方法论里摘出的**平台涨粉逻辑**，全部登记为**待验证假设**，不是结论。
> 写 B站 / 抖音 / 小红书 / 视频号 / 快手模块时，先拿本账号数据去**证伪**，过不了 §四反例 + §五置信度就删掉。
> ⛔ 不要把它们写成「该平台就该这么做」的运营建议——那是创作侧。

| 平台 | 待验证假设（外部口径） | 该用哪个本账号字段去检验 | 状态 |
|---|---|---|---|
| B站 | 垂直度 + 长内容 + 弹幕互动带来涨粉 | 单稿播放 / 涨粉 / 投币 / 弹幕、内容垂直度编码 | ⬜ 未验证 |
| 小红书 | 搜索流量与关键词布局是涨粉主因，收藏率比点赞更重要 | 曝光 / 阅读 / 收藏、笔记来源分层、`V*` 编码 | ⬜ 未验证 |
| 抖音 | 完播率 + 互动率 + 复看率驱动涨粉 | 5 秒完播率、整体完播率、平均播放时长 | ⬜ 未验证 |
| 公众号 | 打开率（标题）+ 搜一搜 SEO + 转发裂变 | `read_user_source`、`read_subscribe_user`、分享率、`T*` 编码 | ⬜ 未验证（见 `wechat.md` §5） |
| 视频号 | 单条动态可直接进四象限 | 单条明细播放 / 关注 / 完播率 | ⬜ 未验证 |
| 快手 | 日粒度数据需先拆净增粉丝 | 净增粉丝量、完播率 | ⬜ 未验证 |

**冲突处理**：外部口径说「涨粉看人设与垂直度」，本 skill 说「涨粉看每千播放涨粉与承接内容」。两者口径不同 → 外部说法只能作为**待验证假设**登记，**不能**直接写进判断层当结论（见 `../hit-methodology.md` §8.3）。
