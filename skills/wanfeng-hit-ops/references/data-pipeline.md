# 数据流水线规范

> 目录约定、归类打分、解析口径、数据源清单。
> SKILL.md 的「三、四步操作」讲怎么用，本文讲**为什么这么定**。

---

## 一、目录结构

```
<data_root>/
├── 临时文件夹/          # 下载收件箱：新下载的文件先丢这里
├── 账号数据/            # 原始数据
│   └── <平台>/<账号>/<YYMMDD>/<文件>
└── 月度报告/            # 结论层：YYYY-MM/
```

### 平台层为什么不能省

同名账号在多个平台都存在（实测：「程序员晚枫」跨 6 个平台，「Python自动化办公社区」跨 2 个平台）。

平铺会同时坏两件事：

1. **同名目录无法区分** —— `账号数据/程序员晚枫/` 到底是哪个平台的
2. **脚本无法从路径反推账号名** —— 解析出来的数据全部挂到错误的账号下

所以结构必须是 `平台 → 账号 → 快照 → 文件` 四层。

### 快照目录（YYMMDD）

一次后台导出 = 一个快照目录。**每次导出另存一份带日期的文件，历史快照永远在**——这是回溯校验的前提，也是能发现「上一轮判断错了」的基础。

- 命名：6 位数字 `YYMMDD`（如 `261128`）
- 同一账号多个快照：解析时**按日期合并去重**（`drop_duplicates(keep='last')`），旧快照不会被新快照整段覆盖
- 账号归属识别：取「向上最近的非 6 位数字目录名」。所以数据放在 `<平台>/<账号>/<YYMMDD>/` 下能正确归属，放在 `<平台>/<账号>/` 根下也能识别

### 文件命名

后台导出的文件**保留平台原始命名**（`user_analysis.xls`、`tendency_*.xls`、`数据表现_短视频全量指标.xlsx` 等），因为解析脚本按文件名匹配。

手工补采的文件用 `数据类型_YYYYMMDD.xlsx`，日期固定 8 位便于字典序排序：

| 示例 | 说明 |
|---|---|
| `粉丝趋势_20260617.xlsx` | 2026-06-17 导出的粉丝数据 |
| `内容表现_20260617.xlsx` | 内容表现数据 |
| `用户画像_20260617.xlsx` | 粉丝画像数据 |

## 二、归类：打分制

新下载的文件先落 `临时文件夹/`，跑 `classify.py` 分派到正确账号。

### 打分项与权重

| 权重 | 判定依据 | 为什么这个权重 |
|---:|---|---|
| **100** | 粉丝末值精确命中该账号归档数据的末值 | 最硬的证据，同一账号同一时点的粉丝数不可能撞 |
| **90** | 净增序列在 ≥10 天上与该账号完全一致（≥95% 相等） | 次硬的证据，序列级吻合 |
| **85** | 整表数值逐行比对，≥3 行且 ≥60% 相同 | 适合渠道分布、文章排行这类无日期列的表 |
| **80** | 内容标题与该账号归档文件重合 | 稿件标题唯一性高，但可能撞车（同一选题跨平台） |
| **60** | 文件名或内容里直接出现账号名 | 弱证据，可能只是碰巧提到 |
| **45** | 单条播放量落在该账号当日总播放之下 | 最弱的量级包含，容易成立，所以分数最低 |

### 判定门槛

- **最高分 < 45** → 留在原地，打印「不足以判定」
- **次高分 ≥ 最高分 × 80%** → 留在原地，打印「多个账号得分接近」

**为什么不猜**：归错账号比不归更危险。错误的归属会被后续所有脚本当成事实，污染每一份报告，而且很难被发现——因为数字看起来完全合理。

### 平台识别

先按**强特征**（表头里出现即锁定），识别不出再按**弱特征**（文件名/表头关键词）。

强特征：`游客播放占比`、`粉丝观看率`、`投币量`、`空间访客`（B站）· `投稿量`、`2秒跳出率`、`主页访问量`（抖音）· `观看量`、`涨粉`、`首次发布时间`（小红书）· `阅读人数`、`累积关注人数`（公众号）· `关注者总数`（视频号）· `作品量`、`完播率`（快手）

## 三、解析口径

### 通用规则

1. **同一账号多快照按日期合并去重**，不整段覆盖
2. **原始导出与页面摘录分开**：`页面摘录*`、`近期稿件对比*` 这类文件字段不是日趋势，不参与趋势计算
3. **平台目录按前缀模糊匹配**：`bilibili-B站` / `B站` / `bilibili` 都能认

### B 站三种口径不可混算（踩过的坑）

| key | 源文件 | 口径 |
|---|---|---|
| `history` | `历史累计数据趋势*.csv` | 累计值（播放量、累计粉丝都是累计口径） |
| `recent` | `近30天数据趋势*.csv`、`近90天数据趋势_播放.csv` | 当日增量（播放量=当日播放，净增粉丝=当日净增） |
| `fans` | `近90天数据趋势_粉丝.csv` | 关注数（粉丝总数、新增关注、取消关注） |

**踩坑记录**：三者字段名互不相同但日期区间高度重叠。早期版本把它们拼在一起做日期去重，`drop_duplicates(keep='last')` 把先到的整段冲掉——90 天的播放数据直接消失，播放列全空。

现在 `parse_bilibili()` 按账号分三个 key 返回，**不要手动 concat**。

判定方式：
- 有 `累计粉丝` 列 → `history`
- 有 `粉丝总数` 列 → `fans`
- 其余 → `recent`

### 公众号的 HTML 伪 xls

`user_analysis.xls` 不是真 xls，是 HTML 表格。**不能用 `pd.read_excel` 直读**，用正则提取 `<th>` 单元格。

`tendency_*.xls` 是真 xls，用 xlrd 读。

### 抖音作品列表是全量历史

`作品列表导出.xlsx` 有 750 条，最早到 2022 年。**不能整表当本期数据用**——必须按本期窗口过滤，否则 Top 榜会混进两年前的旧作品。

### 小红书的两个口径

- `笔记列表明细表.xlsx` 是**内容累计值**（随发布时间不同，累计时长不同），不等于账号 30 天总流量
- `近30日观看数据.xlsx` 里的 summary 是账号级 30 天总览

两者不可混算。

### 快手

`帐号数据分析明细表YYYYMMDD.xlsx`，字段：日期/播放量/完播率/净增粉丝量/评论量/点赞量/分享量/作品量。

> 同一次导出下载两次会得到 md5 不同的两个 xlsx（容器内时间戳不同）。判断重复要**逐格比对内容**，不能比 md5。

## 四、平台导出能力速查

| 平台 | 可导出内容 | 文件形态 |
|---|---|---|
| 微信公众号 | 关注趋势、阅读趋势、渠道分布、文章排行 | `user_analysis.xls`（HTML 伪 xls）+ `tendency_*.xls`（真 xls） |
| 抖音 | 粉丝全量指标、短视频全量指标、作品列表 | xlsx |
| 视频号 | 关注者增长、视频详情、单条动态明细 | CSV（`skiprows=2` 跳过说明行） |
| 小红书 | 笔记明细、近30日观看/互动/涨粉/发布 | xlsx（`header=1` 跳过导出说明行） |
| 快手 | 帐号数据分析明细表 | xlsx |
| B站 | 累计趋势、30/90天趋势、关注趋势、稿件对比 | CSV |

**各平台口径不能直接相加或跨平台排名**：播放/观看/阅读定义不同，分发机制不同。

## 五、新增平台的方法

1. `parse_data.py` 里加一个 `parse_<平台>()` 函数，在 `PLATFORM_PREFIX` 里登记目录名前缀
2. `monthly_report.py` 的 `PLATFORM_SECTIONS` 加段落号与标题，`BLOCK_FUNCS` 加填数函数（返回 `(整体表现, 关键内容表现)`）
3. `classify.py` 的 `PLATFORM_HINTS` / `STRONG_PLATFORM` 里补平台特征
4. 模板 `templates/月度报告模板.md` 里加对应的 `## 4.x` 小节

> 以上是**代码层**（怎么解析、怎么填数）。**分析层**（这个平台的数怎么变成涨粉判断）是另一套：见 [`platforms/README.md`](platforms/README.md) 的扩展契约 —— 复制 `_template.md` 写满 8 节、不得引入联网 / API Key 硬依赖。两层用同一个平台名，互不替代；只加分析模块不加解析代码是允许的，但必须写明数据缺口与补齐方式。
