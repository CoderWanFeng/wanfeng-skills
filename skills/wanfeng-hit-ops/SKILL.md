# 晚枫爆款数据分析（wanfeng-hit-ops）

> **一句话**：把各平台后台导出的原始文件，变成「下期做什么选题」的结论。
>
> **核心主张**：判断内容好坏**不看播放量**，看**每千播放涨粉**与**每千播放收藏**。播放量是分发决定的，涨粉与收藏才是内容价值决定的。
>
> **⛔ 能力边界（最高优先级，先于以下所有规则）**：本 skill **只做数据分析与归因评估**。
> - ✅ **输出**：口径字典、效率指标、四象限、共现特征、反例、置信度、**对已发布标题 / 内容的结构打标与评估**、下期**验证方向**（带判断指标与观察窗口）。
> - ❌ **不输出**：新标题或备选标题、标题优化建议、脚本 / 口播稿 / 正文、封面文案、选题灵感、内容日历 / 发布排期、变现方案。
> - 从外部方法论借来的「标题结构 / 价值类型 / 指标诊断」等维度，**只用于给已发布内容打标签、分组、统计、评估**，严禁反向拿来「生成一个更好的标题或内容」。
> - 用户要创作时，明确告知这属于 `wanfeng-writing-partner`、`hot-topic-radar` 等下游 skill，本 skill 不代做。

> **三个不可让步的纪律**：
> 1. **不跨平台相加播放/观看/阅读** —— 各平台定义不同、分发机制不同，相加得出的排名没有意义。
> 2. **口径必须显式声明** —— 原始导出 vs 页面摘录、日趋势 vs 累计值，同一份报告里混用会得出错误结论。
> 3. **算出来的与人写的分开** —— 数字交给脚本，判断交给人，脚本不许编结论。
>
> **第 3 条的实现方式**：计算层（`scripts/analysis/`）产出的是**带数据和依据的发现条目**
> （现象 / 数据 / 判断 / 置信度依据 / 反例），不是成品结论。
> 脚本负责把「数据能支撑什么」算清楚，**不负责决定「这条重不重要、下期该做什么」**。

## 〇、适用与不适用

### 适用

- 手上有多个平台（公众号 / B站 / 抖音 / 小红书 / 视频号 / 快手）的后台导出文件，要做统一分析
- 已经知道内容表现，但想知道**爆款的共同结构**，以及**伪爆款为什么不算爆款**
- 要出一份能对外汇报的周期复盘（月度 / 季度）
- 要为下期选题设计可验证的实验，而不是凭感觉试
- 新下载了一堆文件，不知道该放哪、怎么归类

### 不适用

- 只想要一张「播放量排行榜」—— 直接看平台后台即可，跨平台没有可比性
- 只分析一个平台且只有累计值、没有任何增量数据 —— 只能出规模描述，出不了归因
- 想要「爆款预测模型」—— 本 skill 做的是归因与实验设计，不是预测
- 内容还没发、要的是选题灵感 —— 用 `hot-topic-radar` / `aihot-topic-selector`
- 要起标题 / 改标题 / 备选标题 —— 属于内容创作，本 skill 只**评估已发布标题**的结构与表现，不生成
- 要脚本、口播稿、正文、封面文案 —— 用 `wanfeng-writing-partner` / `cover-hero` 等下游 skill
- 要内容日历、发布排期、变现方案 —— 都不在本 skill 范围

## 一、整体流程

```
新下载的文件
    ↓
[① 归类] classify.py      临时文件夹 → 账号数据/<平台>/<账号>/<YYMMDD>/
    ↓
[② 解析] parse_data.py    各平台原始文件 → 结构化 DataFrame
    ↓
[③ 归因] analysis/         效率指标 · 四象限 · 集中度 · 相关性 → 结构化发现
    ↓
[④ 成稿] monthly_report.py 发现自动填入报告 + 判断层人工写 → 月度报告
```

> **① 是可选的**（已有规范归档时跳过）；**②③④ 都依赖 ① 的目录结构**。
> 全流程细节见 [`references/data-pipeline.md`](references/data-pipeline.md)。

### 三层分工

| 层 | 在哪 | 产出 |
|---|---|---|
| **规则层** | `references/` | 「怎么判断」—— 指标定义、象限切分、置信度标准、实验设计 |
| **计算层** | `scripts/analysis/` | 「算出来」—— 效率指标、四象限、集中度、相关性、发现条目 |
| **判断层** | 由你（AI）写 | 「说明什么」—— 结论含义、优先级、行动取舍 |

**规则层不写代码、计算层不写结论。** 计算层只产出带数据和依据的发现条目，
判断由人做 —— 这样「哪句是数据、哪句是推断」在文档里物理隔离。

> ⚠️ **计算层能自动填的**：结论摘要、数据事实、分析判断、结构拆解、
> 关键内容表现、反例、数据范围表、缺口表、置信度分级、候选验证方向。
> **仍需人工的**：跨平台取舍的最终判断、第六章的采纳决策、
> 以及任何超出「已发布内容评估」范围的创作动作。

### 目录结构（运行时的样子）

```
<data_root>/
├── 临时文件夹/          # 下载收件箱：新下载的文件先丢这里
├── 账号数据/            # 原始数据：平台/账号/YYMMDD快照/文件
│   ├── bilibili-B站/程序员晚枫/261128/近90天数据趋势_播放.csv
│   ├── wechat-公众号/晚枫AI学习笔记/261128/user_analysis.xls
│   └── ...
├── 月度报告/            # 结论层：按月归档
│   └── 2026-11/月度报告_2026-11.md
└── 脚本/                # 本 skill 的脚本（或软链到 skill 目录）
```

> ⚠️ **平台层不能省**。同名账号（如「程序员晚枫」）在 6 个平台都存在，平铺会导致同名目录无法区分，脚本也无法从路径反推账号名。

## 二、开工前必须确认的三件事

按「一问一答」原则，每轮只问 1 个关键问题。

### 问 1：数据根目录在哪？

默认 `<当前工作目录>`。若用户有既有的运营数据目录，用 `--root` 指定。

```bash
python scripts/monthly_report.py --root /path/to/运营数据
```

### 问 2：要分析哪个月？

默认当前月。可用 `--month 2026-11` 指定。**报告的统计周期按报告月算**，不是按数据文件的最早日期——各数据源的真实覆盖区间会在「数据范围与可信度」表里逐条列明。

### 问 3：这期是「只看数据」还是「出报告」？

| 用户想要 | 做什么 |
|---|---|
| 只想知道哪类内容涨粉效率高 | 跑 ②③，读终端输出，直接回答 |
| 要一份能发的复盘 | 跑 ②③④，生成报告后**由你**把判断层写完 |
| 要下期验证方向 | 跑 ②③，给出**待验证方向 + 判断指标 + 观察窗口 + 样本量**（实验设计）。只说「验证哪个结构是否有效」，**不给具体标题、脚本或选题** |

> ⚠️ 「验证方向」≠「选题清单」。例如写「验证『标题含具体额度』这一编码在公众号是否提升每千阅读涨粉（n≥3，7 天窗口）」是对的；写「下期做 3 条 GLM 免费领 Token」就越界了。

## 三、四步操作

### 步骤 ① 归类（可选）

```bash
# 预览（默认，不移动文件）
python scripts/classify.py --root <data_root>
# 确认无误后执行
python scripts/classify.py --root <data_root> --apply
```

**归类器的工作方式**：先按平台特征词典判文件来自哪个平台，再用账号指纹（粉丝末值 / 净增序列 / 整表数值 / 内容标题 / 字面账号名）给候选账号打分，取唯一最高分。

**判不准时文件留在原地不移动**，并打印原因让人确认。这是刻意的——**归错账号比不归更危险**，因为错误会被后续所有脚本当成事实。

> 判定门槛与打分权重见 [`references/data-pipeline.md`](references/data-pipeline.md) §归类。

### 步骤 ② 解析与校验

```bash
python scripts/parse_data.py --root <data_root>
```

输出每个平台解析到多少行、账号是否被正确识别。**先看这里**，确认无误再往下走。

> ⚠️ **本机系统 Python 没有 pandas/openpyxl/xlrd**，用 `uv run` 带依赖执行：
> ```bash
> uv run --with pandas --with xlrd --with openpyxl python3 scripts/parse_data.py --root <data_root>
> ```

**B 站三种口径不可混算** —— 这是踩过一次的坑：

| key | 源文件 | 口径 |
|---|---|---|
| `history` | `历史累计数据趋势*.csv` | 累计值（播放量、累计粉丝都是累计口径） |
| `recent` | `近30天数据趋势*.csv`、`近90天数据趋势_播放.csv` | 当日增量 |
| `fans` | `近90天数据趋势_粉丝.csv` | 关注数（粉丝总数、新增关注、取消关注） |

三者字段名互不相同但日期区间高度重叠，混在一起做日期去重会把先到的整段冲掉。`parse_bilibili()` 按账号分这三个 key 返回，**不要手动 concat**。

### 步骤 ③ 爆款归因

```bash
python scripts/analyze.py --root <data_root> [--month 2026-11] [--save]
```

回答三个问题：

| 问题 | 判定依据 |
|---|---|
| **哪些是真爆款？** | 每千播放涨粉、每千播放收藏 —— 不是播放量 |
| **哪些是伪爆款？** | 播放高但每千播放涨粉低（看热闹的流量） |
| **哪些是被算法埋没的好内容？** | 完播/互动率好但播放低 —— 值得复用的选题 |

计算层实现在 `scripts/analysis/`：

| 模块 | 产出 |
|---|---|
| `schema.py` | 各平台单作品表 → 统一内容表（口径归一：播放/观看/涨粉字段名统一） |
| `efficiency.py` | 每千涨粉/收藏/互动、中位数四象限、P75 基线、小基数防线 |
| `concentration.py` | 帕累托集中度、标题特征分组对比、关键词分组 |
| `relations.py` | 相关性矩阵（含小样本告警与极值剔除）、触达 vs 效率、涨粉路径拆解 |
| `findings.py` | 结构化发现条目（现象 / 数据 / 判断 / 置信度依据 / 反例） |
| `pipeline.py` | 编排：解析结果 → 全部计算 → 发现条目 |
| `selftest.py` | 回归自检：用历史人工核对过的数字校验计算层没被改坏 |

> **归因方法论与阈值**见 [`references/hit-methodology.md`](references/hit-methodology.md)。
> **改计算层后必须跑自检**：
> ```bash
> uv run --with pandas --with xlrd --with openpyxl python3 scripts/analysis/selftest.py \
>     --root <data_root> --month 2026-11
> ```

### 步骤 ④ 出月度报告

```bash
python scripts/monthly_report.py --root <data_root> [--month 2026-11]
```

产出 `<data_root>/月度报告/YYYY-MM/月度报告_YYYY-MM.md`。

**三层填充**：

| 层次 | 谁填 | 内容 |
|---|---|---|
| 数据层 | 脚本自动 | 粉丝总览表、数据范围表、各平台整体表现、Top 内容榜、数据文件清单 |
| 分析层 | **计算层自动** | 结论摘要、数据事实、分析判断、结构拆解、关键内容表现（带效率指标）、反例、跨平台结构规律、平台分工、数据缺口、置信度分级、候选验证方向 |
| 判断层 | **你（AI）** | 跨平台取舍的最终判断、第六章采纳哪条验证方向、以及任何超出「已发布内容评估」的动作 |

**你仍然要写判断层。** 计算层给的是带数据和依据的发现条目，
你要做的是判断「哪条最重要、下期采纳哪个方向、这份结论对外怎么讲」。

> 判断层写法、章节规范、置信度标注规则见 [`references/report-spec.md`](references/report-spec.md)。

## 四、平台分析模块（按平台扩展）

> 通用方法论管「怎么判断」，平台模块管「这个平台的数到底怎么算」。
> **一个平台一个文件，互不混算**；后续给每个平台单独加能力，只加文件，不改通用方法论。

### 四层规则

| 层 | 文件 | 管什么 | 能否被覆盖 |
|---|---|---|---|
| **L0 能力边界** | 本文开头「⛔ 能力边界」 | **只做数据分析与归因评估，不创作任何内容** | ❌ 最高优先级，先于以下所有规则 |
| **L1 通用纪律** | 本文开头「三个不可让步的纪律」 | 不跨平台相加、口径显式、算的与写的分开 | ❌ 不得违背 |
| **L2 通用方法** | [`references/hit-methodology.md`](references/hit-methodology.md) | 效率指标、四象限、反例、置信度、实验设计、§八 评估编码 | ❌ 平台模块只做具体化 |
| **L3 平台模块** | `references/platforms/<platform>.md` | 该平台口径字典、涨粉漏斗、采集时机、专属分析动作 | ✅ 只在本平台内生效 |

### 路由规则（每次分析前必做）

1. 从 `账号数据/<平台>/` 路径或提问判断平台
2. 加载 `references/platforms/<platform>.md`
3. **未实现的平台**：按 L0 + L1 + L2 出结论，并在报告「数据缺口」写明「该平台尚无专属模块，本次仅用通用口径」，**不许临时现编平台规则**
4. 多平台一起分析：各加载各的模块，分节写；报告第五章「跨平台综合」只做定性分工，不做数值排名

### 模块清单

| 平台 | 模块 | 状态 |
|---|---|---|
| 微信公众号 | [`references/platforms/wechat.md`](references/platforms/wechat.md) | ✅ 已实现：涨粉漏斗 / 单篇归因 / 来源分层 / 反例对照 / 对标与体检 |
| B站 / 抖音 / 小红书 / 视频号 / 快手 | — | ⬜ 待加（按 `references/platforms/_template.md` 的 8 节骨架逐个补） |

> 索引与扩展契约见 [`references/platforms/README.md`](references/platforms/README.md)。新增模块后同步更新本表、本文「八、目录」与 `README.md` 版本表。

### 新增一个平台模块

复制 `references/platforms/_template.md`，**写满 8 节**：适用范围与边界 / 口径字典 / 涨粉漏斗 / 效率指标翻译 / 单篇级归因 / 专属分析动作 / 样本量与实验设计 / 报告落点。

## 五、爆款归因的核心口径

这是本 skill 最有价值的部分，**任何分析都必须落到这几个指标上**。

### 四个核心指标

| 指标 | 公式 | 说明什么 |
|---|---|---|
| **每千播放涨粉** | 涨粉数 ÷ 播放量 × 1000 | 内容有没有让人想「以后还看」 |
| **每千播放收藏** | 收藏数 ÷ 播放量 × 1000 | 内容有没有「值得留着以后用」的信息密度 |
| **每千播放互动** | (点赞+评论+分享+收藏) ÷ 播放量 × 1000 | 内容有没有引发动作 |
| **取关率** | 取消关注 ÷ 新增关注 | 涨粉是不是真的留住了 |

### 为什么不用播放量当成绩

播放量由**分发**决定，不由**内容**决定。分发受账号权重、时段、平台活动、热点运气影响。看播放量会把「被推了一把」误当成「选题好」。

真实案例（2026-10 视频号样本）：

| 内容 | 播放 | 每千播放涨粉 |
|---|---:|---:|
| 免费用GLM-5.3，人人可用 | 82,368 | 9.87 |
| 做方案不用来回切软件 | 75,988 | 1.83 |

**播放量相近，涨幅差 5 倍**。前者是选题结构好，后者是分发给了量但没给价值。

### 三类内容要分开看

| 类型 | 特征 | 该怎么做 |
|---|---|---|
| **放量内容** | 播放高、每千播放涨粉低 | 判定为触达型，不带关注转化 |
| **承接内容** | 播放中等、每千播放涨粉/收藏高 | 判定为高价值型，是账号护城河（是否系列化由内容侧决定） |
| **埋没内容** | 播放低、完播/互动率高 | 判定为「题材有效但分发不足」；**本 skill 只给这个判定，不代做重发或改标题** |

**只做放量内容，账号会虚胖；只做埋没内容，账号起不来。要两条线并行。**

> 象限划分用**中位数**而不是绝对播放阈值。用 1000 播放硬切，会把「无效爆款」和「高质量内容」划进同一组。

## 六、写判断层时的硬规则

1. **数据事实与分析判断分开写。** 「数据事实」只写数字与倍数关系；「分析判断」才写含义、原因、下一步。混在一起读者分不清哪些是数据、哪些是你的推断。
2. **每条判断标置信度（高/中/低），并说清依据。** 「高置信度」的标准是：有完整口径 + 可交叉验证 + 有反例检验过。
3. **必须写反例。** 只列成功案例的报告没有信息量。每节末尾的「反例」是这一节最值钱的部分——它告诉你哪条规律有边界。
4. **样本量小的结论要标出来。** 2 篇内容的表现不能推导成「所有这类选题都会成功」。
5. **数字之间不跨平台排名。** 视频号 13,782/天 和 抖音 7,199/天 不可比；要比就比**同平台内的效率指标**。
6. **发现矛盾先说出来。** 两个数据源打架时，**显式列出矛盾并说明你采信哪个、为什么**，不要偷偷挑一个顺眼的用。
7. **判断层里不许夹带创作。** 结论只能写「哪类已发布内容的哪类结构更有效 / 待验证」；不写新标题、不写选题清单、不写脚本或封面文案。写法示例见 [`references/hit-methodology.md`](references/hit-methodology.md) §八。

## 七、常见失败与兜底

| 现象 | 根因 | 怎么办 |
|---|---|---|
| 解析报 `FileNotFoundError` | `--root` 指错，或文件不在预期目录 | 先 `ls` 确认目录，再重跑 |
| `ModuleNotFoundError: pandas` | 系统 Python 没装依赖 | 改用 `uv run --with pandas --with xlrd --with openpyxl` |
| 公众号 `user_analysis.xls` 读不出 | 它是 HTML 伪 xls | 脚本已用正则提取，勿改用 `pd.read_excel` 直读 |
| B站某文件解析出 0 行 | 该文件是「近期稿件对比」或「页面摘录」，字段不是日趋势 | 脚本已跳过；若需分析稿件对比，另取原始表人工看 |
| 报告里平台数偏少 | 某平台当期无粉丝总数导出 | 正常，会在粉丝总览表下方自动标注「未取得粉丝总数」 |
| 归类器把文件留在原地 | 分数不足或两个账号接近 | 人工确认后放进 `账号数据/<平台>/<账号>/<YYMMDD>/`，再重跑解析 |

## 九、与其他 skill 的衔接

```
[wanfeng-hit-ops] 账号数据 → 爆款归因 → 月度报告 → 下期验证方向
    ↓ 结论回流
[hot-topic-radar] / [aihot-topic-selector]  按结论去选题
    ↓
[wanfeng-writing-partner]  公众号长文
    ↓
[cover-hero]  配图
```

**这个 skill 站在内容生产链路的「起点之后」**：它不产生内容，它产生**「哪类已发布内容有效、下期该验证哪个结构」的数据判断**。这条链路里，本 skill 只负责**分析与评估**：

- 上游 `hot-topic-radar` / `aihot-topic-selector` 给选题灵感（本 skill 不给）
- 本 skill 给「哪类结构涨粉效率高 / 待验证」的结论
- 下游 `wanfeng-writing-partner` / `cover-hero` 负责把选题变成标题、正文、封面（本 skill 不代做）

**判断往下游传，内容不往回写。** 若用户在本 skill 里要标题、脚本或选题清单，明确回绝并指到对应下游 skill。
